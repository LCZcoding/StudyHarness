## 2026-10-15 · 业务定位（已确认）

**一句话业务定义（用户原话）**

> 别人做的是「让 AI 更懂用户」——烂大街。我做的是「让用户真的学会」。

**推论（修正了此前的层级错误）**

- 系统核心不是「AI 的记忆」，而是「**用户的掌握度**」。
- 记忆（会话、历史）从「产品」降级为「**底座**」：记不住你错哪道题的教练，排不出复习计划。
- 因此此前唯一的记忆实现（Kryo 文件 + 内存 Map）不是要推翻，而是要扶正为底座。

**边界声明（写进 README 与面试口径）**

- 系统能度量的是**回忆表现**（答没答对、第几次答对、间隔多久），**证明不了内化**。
- 主动承认这个边界＝进场优势；只喊「AI 帮你学习」的人说不清自己能证明什么。

## 学习机制 · 四桶归类（2026-10-15 已确认）

| 桶           | 内容                                                           |
| ----------- | ------------------------------------------------------------ |
| 做成功能        | 主动回忆自测、遗忘曲线调度、费曼式复述挑漏洞、交错练习队列                                |
| 当设计原则（不是功能） | 降认知负荷 → 一次只给 3 道题、一屏只放一个任务；好奇心驱动 → 落在 prompt 层：先问用户想搞懂什么，不硬塞 |
| 进 C 类（不做）   | 睡眠 / 运动 —— 聊天 Agent 交付不了，顶多做提醒，成本高、价值低                       |
| 只进叙事        | AI 自主发现「你没想到的问题」—— research 级，12 月前做不出                       |

## 最小闭环（复用已有资产，不重写）

> RAG 存材料 → 出 3 道主动回忆题（不给答案）→ 用户复述 + AI 挑漏洞 → 新表记成绩 → 定时任务按遗忘曲线排复习 → 回到出题（交错练习）

每步的资产映射：

| 步骤     | 复用什么                  | 新增什么                       |
| ------ | --------------------- | -------------------------- |
| 收料     | 现有 RAG / VectorStore  | —                          |
| 出题、挑漏洞 | 现有 ChatClient + 提示词体系 | 出题/评判专用提示词                 |
| 记成绩    | —                     | 新表 test\_record            |
| 排复习    | —                     | 新表 review\_schedule + 定时任务 |

**角色分工（回应「AI 不能保证用户学会」的质疑）**

- 用户侧负责**产出**：写、答、复述 —— 知识只有从你嘴里出来才长在你脑子里。
- AI 侧负责**评判与调度**：挑漏洞、记成绩、排复习。
- AI 不能保证内化；它能保证的是「在该回忆的时候叫你」＋「你没法用假装懂糊过去」。

## 业务交互定义（2026-10-15 定稿冻结）

> 定稿后不再重开。发现偏差走**版本化修订**（在下方补一行说明，不覆盖原记录）。

**三种会话模式**

| 模式     | 触发       | 干什么                                           |
| ------ | -------- | --------------------------------------------- |
| ① 自测会话 | 用户带着材料来  | 从材料出 3 道回忆题 → 用户凭记忆答 → AI 只挑漏洞、**不给答案** → 记成绩 |
| ② 自由问答 | 用户随时提问   | 复用现有 RAG 直接回答（不是测验）                           |
| ③ 复习会话 | 定时任务到点拉回 | 从 `review_schedule` 取题 + **交错混排**另一主题 + 关联提问  |

**「构建知识网络」的 MVP 真身**：交错混排 + 关联提问（例：上次错的复利题 + 本周的通货膨胀 + 「这两者什么关系？」）。知识图谱可视化仍留在 C 类，不夸大。

**用户提问的来源（三个）**

- 对材料的疑问 → RAG 检索 `knowledge_item`
- 对错题 / 成绩的疑问 → `test_record`
- 自由好奇 → 模式 ② 兜底

**已拍板：自测中途用户提问 → 选 A**

- 先回答用户，但该题记为「**求助过**」；复习时优先重问它。
- 理由：诚实记录，不憋用户（用户本人拍板）。
- 否决：B（拒绝回答、逼他先写完）／C（只给线索不给答案）。

**资料接入分层**

| 层       | 内容                        | 时机                    |
| ------- | ------------------------- | --------------------- |
| 第一层     | 用户上传 / 粘贴自己的笔记            | 立即（第一个用户就是他自己，冷启动不存在） |
| 第二层     | AI 搜索 → 给链接候选 → 用户勾选 → 导入 | 排在第一条纵切（记忆落库）之后       |
| Backlog | 其他来源（公众号、播客、视频等）          | 不进 MVP                |

- 第二层**不是新需求**：项目已有 `WebSearchTool`(Tavily) / `WebScrapingTool` / `ResourceDownloadTool` / `FileOperationTool`，属于「串流程 + 加个勾选」，也就是他三分法里的 A 类「多源接入」。
- **没有材料的用户**：MVP 阶段要求必须有材料——「从**你的**材料出题」是这个产品的立身之本，否则退化成满大街的泛化 AI 问答。（可选降级「无材料模式」：仅凭模型知识出题并标注，暂不做。）

**版本化修订 ①（2026-10-16）——练习模式**

- **原判断（不覆盖，留档）**：练习模式进 backlog、MVP 不开发；理由是「没有客观验证器，判分靠不住」
- **修正（用户提出，已采纳）**：AI 只负责「给指引 + 指导」，编译 / 跑测试是外部工具的事，用户自己去做 → **技术上不需要执行器，成本 ≈ 一段引导提示词**
- **修正后的定位**：练习模式**进 MVP**，但它是「模式② 自由问答的引导式入口」，**不产生成绩数据、不进复习闭环**（成绩闭环仍只由自测模式供给）
- **修正后的真代价**：练习模式的反馈发生在**系统外部**（编译器 / 终端），系统看不见结果 → 无法记录成绩。故它不进闭环，也不占用 MVP 主干（主干仍是「主动回忆 + 简化调度」两条）
- **表设计影响**：`mode` 加 `PRACTICE` 一个值（只改 `CHECK`，表结构不动）；`type` 先不加

**版本化修订 ②（2026-10-21）——产品说明书写成，业务口径以它为准**

> 与 ① 同样的规则：本节只说明「改了什么、为什么」，上面 2026-10-15 的原文一字不动。

- **产物**：新增 [`product-spec.md`](./product-spec.md)，把散落在对话里的业务决定收成一份可评审的说明书；
  [`mvp-backend-guide.md`](./mvp-backend-guide.md) 按它**整篇重写**（阶段 0~7 + 评测集 + 前端清单 + 技术债）。
- **改动 1 · 任务形态**：旧版只有「回忆题」一种。现改为 **`FACT` 明确问题 + `EXPLAIN` 讲解任务**两类可判分；
  「引导实践」不是题型，是 **`PRACTICE` 会话模式**（独立入口 `/practice/guide`，不判分、不进闭环）。
  原因：一份材料里「能讲出来」比「能答对」更接近学会，费曼式讲解必须成为一等公民。
- **改动 2 · 发起方式**：旧版是「定时任务到点拉回」。现改为 **侧栏待办列表**，用户自己点
  （到期复习 / 需要重讲 / 还没测过）。**否决**自动弹窗与顶部提示条 —— 用户明确说「不要这种方式」。
- **改动 3 · 资料归属粒度（修正了此前文档的设计错误）**：旧版把 `knowledge_item_id` 加在 `t_conversation` 上。
  `REVIEW` 会话会混入另一份资料的题，会话级归属会记错账 → 改为**题目级**
  （`t_question.knowledge_item_id`），会话表不加这一列。
- **改动 4 · 复习排期挂题不挂成绩**：`t_review_schedule` 以 `question_id` 唯一，
  重复作答 / 补讲 / 复习重问时排期行**迁到新题**，而不是按 `test_record` 一行一条
  （否则答一次排三条、补讲再排三条）。
- **改动 5 · 知识点两态**：新增 `t_knowledge_point`（`CANDIDATE` → `VERIFIED`），
  **只从题目的 `target` 抽，不从闲聊抽**。原因：流式输出与结构化抽取不能在同一次调用里完成；
  且闲聊里「我听说过」没经过验证，拿去做类比会教出错误类比。
  迁移的真身 = 出题时注入该用户最近 5 个 `VERIFIED` 知识点，要求做类比。
- **改动 6 · 判分与补讲上限**：`PASS` 按 1→3→7 递进；`PARTIAL` 3 天、`FAIL` 1 天；
  `PARTIAL` 返回 2~4 条**漏洞清单且不给答案**，补讲上限 **1 次**；
  求助记在题目上（`t_question.help_used = true`，先回答再记账，不改判分）。
- **改动 7 · 进度指标定稿**：已掌握资料数 + 连续学习天数 + 待复习数 + 近 8 周讲解次数柱状图；
  **否决**积分 / 等级 / 徽章 / 排行榜（与「学会」无关）。
- **改动 8 · 资料接入收敛**：粘贴 + 上传 `.md` / `.txt` / `.pdf`（仅文字层，扫描件入口拒绝）。
  **取消原「第二层：AI 搜索 → 用户勾选 → 导入」** —— 用户拍板「不抓了，引导用户自己下载再上传」；
  理由是官方文档噪声低但仍需人把关，抓取实现与维护成本换不来产品价值。
- **改动 9 · MVP 主干拍板**（对应下方待办第一条）：主干 = **主动回忆测试 + 固定 1/3/7 天调度**，
  上接「待办列表 + 讲解任务」，下接「进度可视化」。SM-2 / FSRS 仍否决。
- **改动 10 · 工具收敛**：聊天可调用的工具从 `allTools`（含真的会执行 `cmd.exe` 的 `TerminalOperationTool`）
  收窄为 **`chatTools`**（联网搜索 / 网页抓取 / 当前时间）。理由：一次聊天不该触发服务器副作用。
- **改动 11 · 运行观测（2026-10-21 增补）**：新增 `t_ai_call`，每次模型调用记一行
  （`scene` / `latency_ms` / `first_token_ms` / `prompt_tokens` / `completion_tokens` / `success`），
  `GET /metrics/summary` 按场景给 P95。**token 拿不到就存 `NULL`，不估算** —— 流式调用是否返回 usage
  取决于服务端，先实测再决定前端怎么显示。
- **改动 12 · 上下文预算（2026-10-21 增补）**：聊天历史从「固定 10 条」改为**按字符预算裁剪**
  （`app.ai.context.max-history-chars`，默认 8000），从最新往前保留、超预算丢最旧。
  **否决滚动摘要**：每次压缩多一次模型调用，与降成本目标冲突，记入技术债。

**版本化修订 ③（2026-10-23）——资料形态从「一份 = 一个学习单元」改为「文档 → 章节」**

> 同一规则：本节只说明改了什么、为什么，上文原文不动。

- **改动 1 · 学习单元下沉到章节**：上传一份文档后按标题切成 N 章，一章一行 `t_knowledge_item`，
  `doc_title` 相同的行属于同一份文档（不建 `t_document`）。切分阈值 8000~12000 字/章，上限 30 章。
  原因：真实讲义一份就是几万字，整份出题只能考到开头几段，后面半本书永远没被考过。
- **改动 2 · 章节三态（未开始 / 进行中 / 已通过）**：只看 `SELF_TEST` 会话出的题；
  有题未答或存在 `FAIL` / `PARTIAL` 为进行中；全部答完且全 `PASS` 为已通过。
  **`REVIEW` 复制出的题不参与判定** —— 否则每次到期复习都会让已通过章节退回进行中，进度数字周期性下降。
- **改动 3 · 摘要下沉到章节**：每章上传时调一次模型生成摘要，失败只置空该章 `summary`。
  代价是上传时长随章节数线性增长（30 章最坏 1~2 分钟），**接受**，前端必须给进度提示。
- **改动 4 · 同名文档直接拒绝**：`doc_title` 在用户下已存在就 `400`，不覆盖。
  原因：覆盖会让旧章节的题目、成绩、复习排期指向已不存在的内容。
- **改动 5 · 章节学习流程**：未开始 → 「开始学习」进阅读页 → 「我读完了，开始检测」/「直接检测」→ 出题。
  **否决**章级强制过关、顺序解锁（不同人时间与熟练度不同，卡住一章就进不去下一章，只会让人放弃）；
  **否决** AI 导读问题（导读答错会让人误以为读偏了，把阅读变成应试）；**否决**整章串讲题。
- **改动 6 · 出题入口收口**：章节卡片只放「开始学习」「怎么练」，出题统一在阅读页发起。
  **否决**章节卡片直接放「考考我」：多一次阅读页停留，换取用户至少扫过一遍正文。
- **改动 7 · 进度指标改名**：「已掌握资料数」改为「已掌握章节数」，口径按改动 2。
- **否决项留档**：不做预览切分结果再确认、不保存阅读进度、不做章节目录树、不加手动重新生成摘要的接口。

**版本化修订 ④（2026-10-23）——模型调用观测的实现方式：显式 `AiCallRecorder`，不用 Spring AOP / Spring AI Advisor**

> 本节是技术选型，不是产品决策；记录是为了避免阶段 6 写到一半再返工重议。

- **做法**：每个调用点显式写 `long t0 = aiCallRecorder.start()` → 原调用 → `recordCall / recordFailure / recordStream`。
- **否决 Spring AOP（`@Around` + 自定义注解）**：切面省掉的只是「计时 + 写库」两行，而观测真正需要的三样数据切面拿不到：
  `userId`（`GradingService.grade` 的参数里没有用户，用 `args[0]` 按约定取等于把参数顺序当契约）、
  `prompt_tokens` / `completion_tokens`（usage 在 `ChatResponse.getMetadata()` 里，切面拿到的是方法返回的
  `Grading` / `String`，`ChatResponse` 已在方法内部丢失）、流式的首 token 与总时长（`@Around` 在方法返回 `Flux`
  的瞬间就结束，那时还没有一个 chunk 发出）。
- **否决 Spring AI Advisor（`CallAdvisor` / `StreamAdvisor`）**：这是与本次需求对应的框架机制
  （项目已有 `MyLoggerAdvisor` 可参考），能直接读 usage 并包住流式，但 `scene` 与 `userId` 仍要在每个调用点
  通过 `.advisors(a -> a.param(...))` 传入，改动量与显式写法相当，且五个 `ChatClient.builder` 都要改成带统一
  advisor 的写法。
- **理由**：本项目五个调用点都要改方法签名（加 `UUID userId`）并换 `responseEntity()`，显式版的改动范围已经确定；
  面试时「调用前后各取一个纳秒时间戳」一句可讲清，切面方案会被追问切点与身份透传，解释成本更高。
- **重议条件**：调用点增加到 10 处以上，或需要在不改方法签名的情况下跨服务统计时，再评估 Spring AI Advisor。
- **顺带**：若只想练 AOP，用在 Controller 接口耗时日志上，与 `t_ai_call` 分开，不混入观测数据链路。
